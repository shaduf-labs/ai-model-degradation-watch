How we read · Updated 13 October 2026

Check service and product state before scoring an answer.

Errors, access, routing, context, safety, and completed answer quality are different outcomes. A model-degradation claim needs a repeated, controlled task comparison.

1. Check the surface and status

Record the provider, app or API, client version, time, selected model, effort, and incident state. A failure to submit is not a wrong answer.

2. Keep the task receipt local

Save the task and expected result, output or error, correction, final artifact, and any route or context data shown. Keep private prompts and work local.

3. Repeat under the same conditions

After recovery, rerun the same task on the same surface and configuration. Change only one variable at a time. Record output and correction burden.

Evidence needed for capability decline

Use a stable task set, model and configuration receipt, repeated runs, a fixed scoring rubric, and a before/after baseline. Preserve task-level failures separately from completed answers. Check for product changes, routing, context, safety behavior, plan access, pricing, or allowance before attributing a difference to capability.

Limits of this run

The provider has declared a specific GPT-6.1 Sol Codex/Work performance event. Public user issues include narrow leads, but no public matched quality series establishes cause or population impact. A 24-task test is cross-sectional and small.
