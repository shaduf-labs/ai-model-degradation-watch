Method · updated 29 October 2026

Record the route and the task before calling it a regression.

A model label does not identify every product, effort setting, route, quota, or tool state. Start by separating a failed request from a completed answer that missed the task.

Read a live API monitor at its stated scope

AI Stupid Level’s 29 October board reports no below-baseline result among 25 API-tested models at 10:31 UTC, with 66 of 75 model-suite detectors armed and none fired. Its method page describes private tasks and a ten-day arming period; nine detectors are not yet armed. This is a current API-side result, not a test of consumer-app prompts, account routing, or a reader’s own task.

Read the NerfBench score as a composite

BridgeBench’s board still shows a 16 October latest session for four tracked models. The public method describes 50 private tasks, three attempts per task, and a frozen first tracked session as the 100% reference. “First tracked” is not necessarily the provider’s release day.

The method weights correctness at 60%, output tokens at 20%, and cost at 20%. A cost reduction can raise the composite even when pass rate falls. Codex does not report cost, so its weights become 75% correctness and 25% tokens. The method requires two complete, comparable sessions outside the 90–110% range on the same side before confirming a change. The public board does not show task outputs or per-session component scores.

The method says each model is tested at least three times weekly. The visible dates do not show that schedule. It also says OpenRouter uses default upstream routing and does not pin temperature. Treat the score as evidence about that tested serving setup; do not attribute it to model weights without further data. See the full 29 October review.

OpenAI’s current Work and Codex path

OpenAI’s 26 October release notes say GPT-6.1 Terra is rolling out in Work and Codex. Some eligible Plus/Pro Work users may see Terra at Medium instead of GPT-6.1 Sol at Light in a default preset. A user comparison should record the selected model and effort, not infer them from a product-family label.

What a useful comparison records

  • Plan/workspace, product surface, selected model and version, effort, and route when visible.
  • Task, prompt or dataset, conversation context, tools, settings, date, and region when relevant.
  • Whether the request completed; final artifact; correctness, safety, latency, and correction burden as separate measures.
  • Quota state, fallback, sample size, repeat variation, rubric, grader, exclusions, and missing data.
  • Provider incidents and community reports as separate evidence streams.

Read evidence at its stated scope

A provider card can show what a provider measured. A status incident can explain an unavailable request. A fixed public monitor measures its own tasks and route. A community post can identify the next test. None alone estimates every user’s experience.

Do not score access as answer quality

OpenAI’s 29 October release notes canceled a planned Pro 200 allowance reduction and raised some Work/Codex allowances. A usage cap can stop work before an answer exists. Save the plan and account-specific usage display, then score only completed tasks. The provider says allowances vary with model, task, and settings.

Separate a status event from a task regression

OpenAI marked a GPT-6.1 Sol API performance event resolved on 27 October. That confirms a declared service event on named API components; it does not identify a model-weight change or a user’s completed-task outcome. For a quality comparison, keep the product surface, model, effort, task, context, and settings fixed.
