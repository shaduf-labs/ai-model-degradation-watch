Method · version, surface, and side effects

Check the test boundary before naming the failure.

A bad result can come from model behavior, product surface, route, tool, permission mode, filesystem, price, allowance, or outage. The evidence has to separate them.

Evidence order

  1. Name the release and surface. Record exact model version, product, client, API, route, plan, and date.
  2. Check status and access. A resolved outage or account limit changes usability, but does not measure capability.
  3. Hold the task fixed. Keep prompt, context, tools, settings, budget, system instructions, and judge stable.
  4. Capture side effects. Record permission mode, sandbox, approval prompts, commands, paths touched, tool output, and final artifacts.
  5. Repeat and compare. Keep run count, failures, valid outcomes, spread, baseline, and controls.
  6. Separate outcomes. Score task quality, safety, scope compliance, final artifact, correction burden, speed, cost, and access independently.
  7. Take a reversible action. Retry, wait, audit, pin, or switch only when the evidence identifies a useful next move.
